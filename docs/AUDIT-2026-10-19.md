# Cybermates audit: promises vs code (2026-10-19)

This was a read-only audit. No app code was changed. I read `src/`, `api/`, `supabase/schema.sql`, `android/` and `vite.config.js`.

**Legend.** `[x]` Done · `[~]` Partial (code exists but is unfinished, unconfigured or limited) · `[ ]` Not done · `[!]` **Claimed but false**: the public wording says more than the code does.

**Caveat.** Supabase, TURN, Stripe and the xAI keys are all unconfigured. Most "Done" items have only been tested locally (BroadcastChannel buses and the `scripts/smoke-*.mjs` / `e2e-mesh.mjs` tests). None has been tested on a live network.

## A. Public X posts

- [~] **Decentralized mesh app for meeting people.** `src/mesh.js` (MeshNode: flooding envelopes, ttl 6) and `src/membership.js` (SWIM-style sharded gossip). However, all traffic actually goes through **Supabase Realtime broadcast** (`src/net.js` SupabaseBus, channel `mesh`). It is a logical overlay that runs on top of one central relay.
- [!] **"Mesh network".** Intended design: a peer-to-peer mesh over the internet (not a MANET). Not yet a true P2P overlay, because every envelope is relayed by Supabase (`net.js:4-6`: "Moving chat envelopes onto WebRTC data channels is a TODO").
- [!] **"Device hardware hash, no login."** "No login" is true: there is no auth, and the identity is a random 10-character code from `newUserCode()` in `vault.js:356`. "Hardware hash" is false. `device-gate.js:2` says "Identity is NOT derived from any device hash". Device info only feeds the vault KDF (`vault.js:294-310`), and `blocklist.device_hash` is an unused column.
- [!] **"No servers, rolling database on phones."** Phones do keep the rolling list (`activelist.js`, `membership.js`). But the app still needs servers: Supabase Realtime carries every message, and Vercel `/api/*` handles bootstrap, kill, ban, Stripe, help and voice. A more accurate phrase would be "no server-side profile or message storage" (`schema.sql` header).
- [x] **Self-healing.** `membership.js` has signed suspicion (`SUSPECT_REPORTS=2`), incarnations, anti-entropy `syncWith` every 60 s and re-ask on `wantTimeoutMs`.
- [~] **Self-formation (server only for first-time jump start).** `api/_fn/bootstrap.js` and `snapshot.js` do the warm start. The jump start works, but steady-state transport is still the server (Supabase).
- [!] **Peer to peer ✅.** `p2p.js` has WebRTC code with relay-only ICE, but the TURN URL is a placeholder (`turn.example.invalid`). The data channel is created (`createDataChannel('chat')`) and **never used**: no `onmessage`, and mesh/chat never send through it.
- [x] **Local data + encryption ✅.** Per-field AES-GCM vault (`vault.js`). The active list and ban list are sealed (`activelist.js`, `banlist.js`).
- [!] **Data transfer + encryption ✅.** Profiles are Ed25519-signed and the 6-digit transfer is AES-GCM (`transfer.js`). But **chat and starter envelopes are plaintext JSON** sent over the Supabase broadcast. The only protection is TLS to Supabase, so Supabase and anyone holding the anon key who subscribes to `mesh` can read them. `mesh.js:137-138` admits "relay-broadcast payloads should be sealed per-recipient — gap". I found no E2E sealing (`nacl.box`) anywhere.
- [!] **Auto spam detection ✅.** **No code exists.** No match for spam, heuristics or scoring in `src/` or `api/`. The closest things are the 500-character starter cap, the 5/day wallet limit, `rateLimit()` on the admin routes only (`api/_lib/mod.js:769`) and manual Report/Block.
- [!] **Sniffing detection ✅.** **No code exists.** Nothing detects interception or MITM. Signatures stop tampering with profiles, rows and controls, but they cannot detect someone reading traffic, and the chat traffic is readable by the relay (see above).
- [!] **Weekly updates that scramble the binaries.** **Not implemented.** There is no obfuscator (no terser or javascript-obfuscator config in `vite.config.js`), and Android has `minifyEnabled false` (`android/app/build.gradle:21`). What does exist is "two-version rotation": the KDF salt/iterations version and `APP_VERSION` (`vault.js` KDF table, `appconfig.js`). That is a protocol/key version, not scrambling. Even if it were built, scrambling would be obscurity, not security (see D).
- [!] **Hops only occur when a user is online actively searching.** **False.** `app-mesh.js:54` pings, gossips and ticks every 20 s, and anti-entropy runs every 60 s, for as long as the mesh is started. `MeshNode.receive` relays every envelope (`mesh.js:44-45`) whether or not the user is searching. The only true part is that there is no background service, so nothing runs while the app is closed or hidden (`wireLeave` on `pagehide`/`visibilitychange`, `membership.js:262`).
- [x] **Internet-based, no Bluetooth/range limits.** There is no BLE code, and transport is HTTPS/WSS.

## C. Fallback bootstrap plan (draft, not implemented) — ❌ SUPERSEDED 2026-10-20 by the single-entry server (see below)

**Goal.** Bootstrap in this order: (1) server, (2) the owner's phone, (3) the cached encrypted active list. The server is re-checked periodically so bans still apply.

### Technical constraints
1. **Phones and browsers cannot accept inbound connections.** They sit behind carrier CGNAT or home NAT, and a PWA cannot listen on a socket at all. Nothing can "dial" the owner's phone directly.
2. **WebRTC always needs a signaling channel** to exchange the SDP/ICE that starts a connection. It also needs STUN/TURN for NAT traversal, and with `iceTransportPolicy: 'relay'` it needs **TURN**. If Supabase is down, some other rendezvous has to carry the offers.
3. **Cached peers can't be reached without signaling.** The active list deliberately stores codes and pubkeys with no IPs, and even IPs would be stale or NATed. On its own, the cached list tells you *who* to look for, not *how* to reach them. It is only useful once **some** alternate signaling channel is up.
4. **A phone as bootstrap must be always on and reachable through a relay.** In practice:
   - **Android:** a native foreground service (persistent notification, wake lock, battery-optimization exemption) holding an outbound WebSocket to an alternate signaling service. Expect real battery drain and OEM task killers (Samsung, Xiaomi).
   - **iOS/iPad:** this is **not feasible**. iOS suspends apps within seconds of backgrounding, and there is no general long-lived socket in the background (VoIP push/PushKit is not allowed for this). The iPad can only act as a client.
   - So the owner's phone is really just *another client of a second signaling service*. That second service is what actually provides the redundancy. The phone adds the signed snapshot and ban list.

### Most realistic design
- **Tier 1: primary server.** Supabase Realtime + `/api/bootstrap`, unchanged.
- **Tier 2: independent secondary signaling plus the owner's "seed node".**
  - Run a second, independent rendezvous so it doesn't share Supabase's failures. Options:
    - a tiny WebSocket relay on a different provider (Cloudflare Workers/Durable Objects free tier, Fly.io), or
    - public signaling (e.g. a self-run PeerJS server, or Nostr relays used as a dumb signed-message bus; Nostr fits well because there are many independent relays).
  - Ship 2–3 endpoint URLs in a **signed config** (same Ed25519 key as `app_config`) so they can rotate without a new release.
  - The owner's Android phone runs the app in **"seed mode"**: a native foreground service connects to the secondary rendezvous and answers `snap-req` with its signed active list plus the current signed ban list.
  - **Seed identity is pinned by a public key**, the same way the server's identity would be. Clients accept snapshots only if they are signed by the seed key; rows are still verified one by one.
  - TURN must come from a provider that is not Supabase (Cloudflare Calls TURN, Twilio, or self-hosted coturn), or the alternate path has no media/data route.
- **Tier 3: cached encrypted active list.** Decrypt with the vault, then announce presence on whichever signaling tier is up and target the cached codes first. If no signaling channel is reachable at all, **show "offline"**. Don't pretend to connect.
- **Periodic server re-check (bans stay effective).**
  - On every start and every 24 h, or every N=5 launches, whichever comes first, try Tier 1 for `kill_switch`, the ban list and `min_version`.
  - Use a **max-offline-from-server budget** (e.g. 72 h). Past it, the client still works with existing friends but stops seeding snapshots and stops accepting new contacts until a server check succeeds. This limits how long a banned user, or a forked client, can operate.
  - The seed node also relays the signed ban list, so bans keep spreading during an outage.
- **Order of steps.**
  1. Try the server (timeout ~4 s).
  2. Otherwise try the secondary signaling and request a seed snapshot (verify the seed signature).
  3. Otherwise use the cached list over any reachable signaling.
  4. Otherwise show offline.

## D. Security assessment (reverse engineering)

Everything shipped (PWA and Capacitor WebView) is readable JS. Minification only slows a reader down. An attacker learns the complete protocol: envelope types, gossip, the snapshot API, the KDF salts and iteration counts, the kill/receipt public keys, the Supabase URL and anon key, and the channel names.

**Protected by real crypto (holds up even if the code is known):**
- Kill, ban and config messages: Ed25519, with the private key held offline by David.
- Stripe receipts: the server signs them and the private key lives only on the server.
- Profile and row signatures: per-user Ed25519 with TOFU pinning.
- The vault at rest on a *different* device: the random install secret makes a copied blob useless elsewhere.

**Protected only by obscurity or client honesty (falls once the code is read):**
- The wallet and daily limits (local; a modified client edits them, although they cannot mint server receipts).
- Burn mode.
- The consent attestation.
- The emulator gate (patchable, and it fails open).
- The voice cap's client timer.
- Display-only counts.
- "Weekly scrambling" if it were ever built.

### Risks
1. **Reading or scraping the mesh.** Anyone with the public anon key can subscribe to the `mesh` channel and read all profiles, presence and **plaintext chats**. This is the top risk.
2. **Forging presence or Sybil accounts.** User codes and keys are free to generate, so an attacker can spawn thousands of signed identities. There is no cost, PoW, attestation or rate limit on Realtime.
3. **Device ID spoofing.** Device info is readable and low-entropy, but it is *not* an identity. The real concern is that bans are per code, and a new code costs nothing. `device_hash` is unused, and would itself be spoofable if it were derived in JS.
4. **Relay abuse and DoS.** There are no per-sender limits on broadcast floods or gossip `ihave` floods, and the 5 MB snapshot POST is open to anyone. Supabase quotas get exhausted and that takes everyone down.
5. **Bootstrap ban bypass.** The client chooses the `code` it sends.
6. **Snapshot poisoning.** Rows are signed but self-issued, so a Sybil can fill snapshots up to 200k rows.
7. **Kill key safety.** The admin page asks David to paste the seed into a browser tab, where any XSS or extension on that page could steal it. The repo ships `DEV_KILL_PUBKEY`, so a forgotten production env var would leave whoever holds the dev seed in control.
   - **Status 2026-10-20: DONE in code (prod key itself still pending).** The admin panel has no key input or signing code; it only accepts pre-signed JSON from `scripts/mod.mjs --out` and verifies it against the public key. `mod.mjs` reads the key only from a passphrase-encrypted keyfile (scrypt + AES-GCM, 0600) outside the repo. It refuses keyfiles inside the project and keys on argv, and the env-var key path was removed. A halt needs `--reason` and typing `HALT`. All signing moved to `scripts/lib/sign.mjs`, which is never bundled. The server holds only the public key and rejects unsigned, wrong-key, stale, replayed-nonce and reasonless halts. Production bundles without `VITE_KILL_PUBKEY` now **fail closed** (no key trusted) instead of falling back to `DEV_KILL_PUBKEY`; the dev key works only on the dev server or with `VITE_ALLOW_DEV_KILL_KEY=1`. The repo and both builds were scanned and contain no private key material (`scripts/smoke-killkey.mjs`). **Still open:** generate the production key (`mod.mjs keygen`) and set `VITE_KILL_PUBKEY` in Vercel. Dev/receipt seeds exist on the box at `/workspace/cybermates-secrets/` (outside the repo, never bundled). Move them to a password manager and delete them from the box.
8. **Transfer code.** 10^6 codes, brute-forceable offline from relayed traffic.

### Hardening, in rough priority order
1. **E2E-seal envelopes** with `nacl.box` to the recipient pubkey. Supabase then only sees routing data. Alternatively, move chat onto the WebRTC data channel with a real TURN.
2. **Supabase Realtime authorization:** private channels plus RLS on `realtime.messages`, short-lived JWTs minted by an edge function after attestation, and per-user broadcast rate limits.
3. **Join cost:** Play Integrity (Android) and App Attest/DeviceCheck (iOS), verified server-side, before a code is allowed into bootstrap. Add proof-of-work on join for web, and per-IP/per-attestation rate limits on `/api/bootstrap`.
4. **Bind ban enforcement to the attestation-derived device ID server-side**, not to the self-reported code.
5. **Move the install secret into Android Keystore / iOS Keychain** (secure-storage plugin) and use non-extractable hardware keys where possible.
6. **Ship native Capacitor builds only for production:** enable R8 (`minifyEnabled true`), sign release builds, and pin the signing certificate in the attestation verdict.
7. **Sign kill/ban messages with the CLI** (`scripts/kill-switch.mjs`) on an offline machine, or with a hardware key, instead of pasting the seed into the web admin. Have the build fail if `VITE_KILL_PUBKEY` is unset.
8. **Use a real PAKE (e.g. CPace/SPAKE2)** for transfer, or show a QR code with a 128-bit secret.
9. **Obfuscation (javascript-obfuscator, weekly reshuffles):** at best a speed bump of days, with performance cost. **It is not security.** Do not market it as security.
10. **Remove or reword the false public claims** ("spam/sniffing detection ✅", "no servers", "P2P ✅", "scrambled binaries", "hops only when searching").

## Owner design decisions (2026-10-19, voice call 3) — notes only, no code changes
### Fallback / reconnect order — ❌ SUPERSEDED 2026-10-20 (single entry: no master-phone / cached-list / seed fallback)
1. Server (Supabase) is the first point of contact.
2. If the server can't be reached: owner's phone acts as relay/master node. The master app must be open to accept connections (intentional).
   - Master profile runs in a separate, unpublished admin app (never distributed) with admin functions.
   - Master credentials stored offline only.
   - If the master phone is ever compromised: rotate keys and roll out new versions of everything.
   - Technical caveat (from audit): phones can't accept inbound internet connections directly, so the master phone still needs a reachable rendezvous (e.g. second signaling service and/or TURN) for other phones to reach it.
3. Last resort: try connections from the phone's existing (encrypted) active list.
   - Caveat: the list holds no IPs, so reconnecting from it still needs some signaling path.
### 24-hour rule
- An active list is stale after 24 hours.
- Phones check in with the server every 24 hours specifically to learn if they were banned, even if they don't pull a fresh list.
- If a phone checked in within the last 24 hours, it may keep using its existing active list to jump-start connections without re-pulling everything.
### Scaling
- Server load grows over time; scale by paying for more connections. Not a concern at launch.

## Ban enforcement logic (2026-10-20, voice call 4)
- Online banned user: booted and banned immediately (signed targeted kill + gossiped ban list). Already implemented (src/ban.js, src/banlist.js).

## Update 2026-10-20: two-key identity, never-send guard, attestation, three lists

### Two-key design (private encryption key vs shareable ID key)

| | **Encryption key** (private hash key) | **ID key** (shareable identity) |
|---|---|---|
| Where | `src/vault.js` (unchanged) | `src/identity.js` |
| Derivation | `PBKDF2_v(SHA256(SHA256(HMAC(installSecret, deviceInfo))), salt_v)` → AES-GCM-256, non-extractable | `SHA-256("cybermates-id-v1" \| platform \| stable device fields)` → 16 chars (~80 bits) |
| Inputs | random install secret (IndexedDB) + device info + KDF version salt | **only** stable device data: Capacitor `Device.getId()` (+manufacturer/model) on native; best-effort browser fingerprint (UA, platform, language, cores, memory, screen, timezone) on web. No install secret, no app version, no randomness |
| Used for | encrypting vault, active list, ban list, block list at rest | network identity: mesh addressing, presence, membership rows, bans, blocks, ban list, active list, server blocklist/bootstrap, reports |
| Leaves device? | **Never** (enforced by the never-send guard) | Yes, it is the public address |

The ID key is never used as or mixed into an encryption key. `?as=<persona>` demo tabs (admin/dev flavor) add a `|persona:` suffix so several demo users on one browser stay distinct.

**Migration:** on first mesh start after upgrade, each stored identity (`vault.meshIds[x]`) gets `code = ID key`. The old random code is kept as `legacyCode`, and signing keys, friends and blocks are kept. Bootstrap/check-in also send `&legacy=<old code>`, so server bans on the old code still apply, and signed bans addressed to either code are honoured locally. If the device fields drift (for example a web fingerprint change), the previous ID is appended to `priorIds`. Peers that cached the old code see the user come back under the new ID, and friendships re-pin when they meet again (TOFU on the same signing key). Payments/receipts still use the vault `userCode` (unchanged API format `[A-Z0-9]{10}`).

**Never-send list** (`src/never-send.js`, `guardOutgoing`). Every mesh bus post (`src/net.js` LocalBus + SupabaseBus), P2P signaling (`src/p2p.js`), app-mesh HTTP (`guardedFetch`) and Supabase profile upsert goes through it:
1. any `CryptoKey` (vault AES key, install-secret HMAC key) → **rejected**
2. the KDF input string (device info, registered by `Vault.key()`) anywhere in a payload → **rejected**
3. a vault ciphertext blob (`{kdf, iv, ct}`) → **rejected**
4. fields named `installSecret`, `devKey`, `deviceKey`, `vaultKey`, `encKey`, `encryptionKey`, `kdfInput`, `deviceInfo`, `hashKey`, `privateKey`, `secretKey`, `sec` → **stripped**

Test: `scripts/smoke-twokey.mjs` (also run by `npm run smoke`).

**Attestation.** `src/attest.js` requests a token bound to the ID (nonce = SHA-256 of `cybermates-attest-v1|id|5-min bucket`). It uses Google Play Integrity on Android (needs a `PlayIntegrity` Capacitor plugin, TODO) and Apple App Attest on iOS (needs an `AppAttest` plugin, TODO). The web has no attestation. `api/_fn/attest.js` is a verification stub: it checks the nonce binding, and the real Google decode and Apple CBOR/cert-chain checks are TODOs. Credentials come only from env vars (`PLAY_INTEGRITY_SA_JSON`, `GOOGLE_CLOUD_PROJECT_NUMBER`, `ANDROID_PACKAGE_NAME`, `ANDROID_CERT_SHA256`, `APPLE_TEAM_ID`, `IOS_BUNDLE_ID`, `APP_ATTEST_ENV`), and nothing is bundled. `api/bootstrap` reads header `x-cm-attest` and **does not refuse** unattested IDs. It returns `{attested:false, flags:['unattested']}` instead. Until verification is implemented, every ID is flagged unattested.

**Tradeoffs:** the web ID is weak: browser updates change it, it can be spoofed, and identical machines collide. A new phone means a new ID, and bans don't follow the person. An Android factory reset (or a different app-signing key) changes `ANDROID_ID`. iOS `identifierForVendor` changes if all the vendor's apps are removed. Without real attestation a modified client can claim any ID. The ID is stable across reinstall on native, so a banned user can't just reinstall, but a reinstall still loses the private key and the encrypted data.

**v44 (2026-10-27) proximity voice transport:** each nearby same-band player gets a real per-peer WebRTC audio link, mixed through its own GainNode at the distance gain (`src/rtc-voice.js`, `ProximityVoice.attach`). Inbound offers are refused unless I want that peer right now (in range, nearest 8, same band, not blocked or muted), so out-of-range or cross-age peers can't open a listening link, and a forced dial from a lying client is refused by the receiver. Open items: TURN, a real-phone check, and the pre-existing one-way mass-arena presence.

**v43 (2026-10-27) identity binding:** the ID is now bound to one signing key (`src/idbind.js`, `api/_lib/idbind.js`). A different key can no longer take over an ID that is already bound, at peers (E2E ping gate, living mesh, membership, gossip) or at the server (bootstrap registry, bound-key logoff/delete). Claiming a *new* ID costs a bounded proof of work (~0.5 s desktop, ~2 s at 4x CPU throttle). **Remaining limits:** someone who computes a victim's web fingerprint can still claim it first if the victim has never joined (first claim wins until a server cert or attestation says otherwise). Mass-minting IDs is slowed by the PoW, not prevented. Until Play Integrity / App Attest verification is real, native phones pay the same PoW as the web.

## Update 2026-10-20: Tiered enforcement (ban levels 1-5)

All enforcement is keyed by the **ID key**. The logic lives in `src/tiers.js` and is shared by the client, `api/` and the admin tools.

| Level | Meaning | Effect | Delivered via |
|---|---|---|---|
| 1-2 | warning | notice on next contact/check-in; user keeps using the app; offense reason recorded (e.g. spam) | server only (bootstrap / 24h check-in returns `{level, warning}`) |
| 3 | final warning | same, notice says the next offense suspends | server only |
| 4 | suspension (default 7 days, `--suspend-days` / admin field) | booted (friends kept), bootstrap returns `403 {suspended, until}` until expiry, then it reads as **level 3** | signed targeted kill `level:4`, `expires_at` = end of suspension; server blocklist + mesh gossip |
| 5 | ban | instant boot, wipe, permanent vault marker (unchanged behaviour) | signed targeted kill `level:5` (legacy entries without a level = 5); server blocklist + mesh gossip |

- **Strikes:** every new offense escalates one level, capped at 5. The admin can also pick a level directly, lower it (`unban --to-level 1-3`, which keeps the record and lifts the signed entry with a signed clear), or remove it entirely (`unban`).
- **Signed fields:** entries carry `level`, `reason`, `strikes` and `expires_at`. `level`/`strikes` are added to the signed canonical form only when present, so old signatures still verify. The compact ban-list encoding is 9 elements for tiered entries and 7 for legacy ones.
- **Mesh:** gossip only propagates and enforces levels 4-5. Phones ignore warning-level messages (`warning-only`) and the ban list rejects them.
- **Server:** `blocklist.level`, `strikes` and `suspended_until` (schema.sql). `isBlocked` means effective level ≥ 4. Bootstrap checks both the ID and `legacy` codes. `mod_actions.level` is logged.
- **Tools:** `node scripts/mod.mjs strike <id> --category spam/scam --reason "..." [--level N] [--suspend-days 7]`, `ban <id>` (= level 5), `unban <id> [--to-level N]`. The admin panel has an Auto/1-5 level picker, suspension days, and lower-to. `/api/ban` takes `{status:true}` for the current standing.
- **Tests:** `scripts/smoke-tiers.mjs` (in `npm run smoke`) covers escalation 1→5, suspension expiry back to 3, warnings not booting, level 5 instant boot, and gossip of 4-5 only.
- **Limits:** in local/demo mode (no server) warnings are recorded but never shown, because check-in is a no-op locally. A suspended user on a new phone gets a new ID. Level 4 relies on the device clock for the local expiry, but the server is authoritative.

## ✅ BUILT 2026-10-20 (mock only) — Random relay rotation / traffic mixing (src/relay.js)

This sits alongside the planned self-healing reconnect and the encrypted packet layer (Ed25519 signatures + AES-GCM payloads).
- **Plan:** phones periodically (every few minutes, and per conversation) pick random multi-hop relay paths (2-3 hops) from the active list. - **Tradeoff:** friend-graph routing makes paths more predictable and weakens mixing. So **require at least one random non-friend hop per path** and keep rotating.
- Unchanged: relay only while the user is online and searching; exclude banned, blocked and unattested peers.

## ✅ BUILT 2026-10-20, WIRED v38 2026-10-27 (RxGate in app-mesh.js bus.on, before unpack/verify/decrypt) — DoS defense: cheap shield (src/shield.js)
- **Principle:** make each phone expensive to overwhelm but cheap to run. That means:
  - small fixed-size packets (relay padding buckets already exist);
  - signature and size checks **before** any other work: drop bad packets fast, before decrypting or decompressing;
  - **no state for strangers:** a stateless challenge/cookie before allocating anything (queues, AES keys, cache rows).
- **Rate limits at the first node:** per sender and per ID, so a single spammer is caught quickly. Repeat offenders feed the **tier strikes** (`src/tiers.js`).
- **Distributed floods** (hundreds of IPs/IDs) can't be fully prevented. The cheap-shield design makes a flood cost the attacker more than the network.
- **Relay abuse** is contained by hop limits (TTL), dedupe IDs (`MeshNode.seen`), the connection cap, and relaying only while searching (`src/relay.js`).
- **Cross-reference to existing audit items:** there are still no per-sender broadcast/gossip limits. The snapshot POST is open and accepts up to 5 MB (`api/_fn/bootstrap.js`; pushes are now sealed, but the size limit is unchanged). The Supabase Realtime quota is a single shared point of failure.
- **Recommend:**
  - server-side per-IP/per-ID rate limits on all `api/` routes (✅ every route via `api/_lib/guard.js`; v40: global across Vercel instances via Supabase `rl_hit`, per-instance fallback);
  - Vercel Firewall/WAF rules on `api/*`;
  - lowering the snapshot POST limit, e.g. to about 512 KB, plus one push per phone per nonce;
  - monitoring and alerts on Supabase quota.

## ✅ BUILT 2026-10-20 (crypto + api/_fn/link.js + tests; no QR UI yet) — Device linking (corrected)
- **Encryption key: per device.** Each device derives its own encryption key from its own hardware plus its own install secret. It is private and never shared or sent, and it stays on the never-send list.
- **Network ID: one per profile.** All devices linked to one profile share **ONE network ID**, used for communication, bans and blocks. The profile stores that shared ID.
- The **first device's** hardware-derived ID key becomes the profile ID. Additional devices receive it through a **signed linking step**: a QR or short code from an existing device, re-keyed for the new device (the profile data is re-encrypted under the new device's own key, as in the existing transfer flow in `src/transfer.js`). The encryption key is never sent.
- A **ban on the shared ID covers all linked devices**.
- Suggested: the server also keeps per-device hardware fingerprints (the `device_hash` column already exists in `blocklist`), so a banned device can't create a fresh profile. Cap the number of linked devices (e.g. 3-5).
- **Superseded:** any earlier idea of a per-device ID list (device 1, device 2, …). No such text was found in this doc or the README; this note is the authoritative version. Current code: the ID key is per device (`src/identity.js`). Linking/sharing one ID across devices is **not built**.


## DONE 2026-10-20 — Single-entry server (David's design change; supersedes all fallback/seed/warm-start items)
**The server is the only entry point.** `api/_fn/bootstrap.js` + `api/_lib/presence.js` hold a rolling **super list** of
online profiles: ID key, owner-signed presence row, mode tags. **No IPs.** It's updated on login, a heartbeat every 60 s,
and logoff (`sendBeacon`); rows silent for more than 3 min expire. Mock store today; table `public.presence` and the
`SupabaseSignal.presence*` adapter are ready (`smoke-presence.mjs`). Phones join only from `GET /api/bootstrap` (mode-filtered, ≤300 rows).
Halt (503), ban/suspension (403) and US-only (451) all gate at that one entry, plus every heartbeat. A banned or
halted phone is also removed from the list.
**Removed in code:** the phone snapshot warm start (`snap-req` broadcasts, `SnapshotCache` ingest of phone pushes,
`snapshotPush`, `src/snapshot.js`, and the 512 KB snapshot POST, now an 8 KB presence POST), the persisted encrypted
active-list file (`src/activelist.js` save/load/shred; the kill now clears memory and purges any legacy file left on old
installs), the cached-list jump-start (`startPlan.useCache`, `freshActiveList`), and the tests `smoke-snapshot.mjs` and
`smoke-warmstart.mjs` (replaced by `smoke-presence.mjs`). There was no master/owner-phone fallback or seed-list code; those notes are now marked superseded.
**Kept:** the in-memory active list (`member.active`, never written to disk), peers already directly linked stay linked if
the server goes down (no new entry until it's back: "SERVER UNREACHABLE · NO NEW ENTRY"), the 24h check-in, and the 24h sweep.
The local BroadcastChannel dev bus has no server (dev/test only).
**Tradeoffs:** the server is a single point of failure for new connections; the server sees who is online (ID key + mode,
no IPs, no content); in exchange, ban, kill and US-only enforcement are simpler and airtight (no side door).

## PLANNED — Scaling to 20k+ devices (⏳ awaiting David's approval; notes only)
- The server's rolling list keeps the last ~200-300 relevant profiles per user, timestamped at **login** (the trigger).
  Offline users stay listed and show as *offline* when someone messages or views them. (Today the list drops a row after
  3 min of silence. Plan: keep it with an `online:false` flag and a longer retention.)
- Sizing: 20k rows × ~140 B ≈ **3 MB**, small for one server or Postgres table. `scripts/sim-20k.mjs` already models 20k
  phones (it still uses the old phone-snapshot download; update it to the server list before quoting numbers).
- Load-distribution options: (1) **server shards** the list by mode, interest category (e.g. gaming/xbox) and optionally
  region; (2) **server-signed slices**: phones fetch only their slice, cache it encrypted in memory, and share the signed slice
  peer-to-peer with nearby phones searching the same shard (signature + timestamp + expiry prevent poisoning), so most searches skip the server;
  (3) **CDN/edge caching** of slices with a short TTL; (4) **mesh traversal**: broadcast discovery within the shard to collect ~200 matches.
- The single-entry rule still holds: login and ban/US/kill checks always go to the server; peer slices are only for search after entry.
- **Recommended order:** (1) + (3) first, (2) later, (4) as an option.
